# Output template

最終報告では、次の5セクションだけをこの順序で出力する。

```md
# AIコードレビュー

## レビュー指摘

### [Must/Should] 指摘のタイトル
- 観点: 挙動・事業・ユーザー / セキュリティ / パフォーマンス / 理解・変更容易性 / レイヤ責務 / 単一責任
- 根拠: `path/to/file:line`
- 発生条件: 問題が顕在化する入力、状態、操作
- 影響: 誰に何が起きるか
- 対応案: 最小限の修正または確認方法
- 確信度: 高 / 中

## パフォーマンス上の計測候補

### [計測候補] 計測する懸念を表すタイトル
- 根拠: `path/to/file:line`
- 負荷増加の仕組み: 差分によって処理量または資源消費が増える経路
- 顕在化しうる条件: データ量、頻度、同時実行数、入力形状など
- 懸念する資源・影響: CPU、メモリ、DB、ネットワーク、I/O、ロック競合、レイテンシなど
- 計測案: 比較する条件、指標、確認方法

## 仕様をアサートするテストの不足

### [高/中] 対象仕様を表すタイトル
- 対象仕様: 変更された仕様または不変条件
- 実装箇所: `path/to/file:line`
- 現在のテスト証拠: 対応するテストと、何を確認しているか
- 不足するアサーション: 明示的に確認されていない結果
- 推奨テスト: 入力・操作と期待結果

## 外部システム契約に依存する確認事項

### [確認] 確認する外部契約を表すタイトル
- 対象システム: 契約を確認する外部システム
- リポジトリ側の前提: 今回の差分が依存する外部システムの挙動
- 外部契約の不明点: リポジトリ内では確認できなかった保証
- 保証されない場合の影響: 問題が生じる応答や状態と、その実質的な影響
- 保証される場合: 対応不要など、候補を除外できる条件
- 確認先: 仕様、資料、担当システムなど、判断に必要な情報源

## AIが判断できなかった点

- 判断できないこと（重要な理由: ... / 確認に必要な情報: ...）
```

## 出力規則

- `Must`は、今回の差分で対応しなければ具体的な不利益が生じうる問題に使用する。
- `Should`は、将来の誤変更やレビュー負荷を実質的に増やす実装に使用する。
- パフォーマンス計測候補には`Must`/`Should`を付けず、負荷増加の仕組みを差分から説明できるが、実害は計測しなければ判断できない事項だけを含める。
- パフォーマンス計測候補では問題や修正の必要性を断定せず、「可能性がある」「計測で確認する」という強さで記述する。
- 抽象的な性能懸念、差分で悪化していない既存負荷、増幅要因のないマイクロ最適化は含めない。
- 実測値、明示されたSLO、既知の上限などがあり、通常の証拠基準と重要度基準を満たす場合は、パフォーマンス計測候補ではなく通常のレビュー指摘として扱う。
- 性能テストやベンチマークがないことだけを、仕様をアサートするテストの不足として重複報告しない。
- 外部システムの契約次第で正否が変わる候補には`Must`/`Should`を付けず、「外部システム契約に依存する確認事項」へ分離する。
- 外部契約の確認事項は、今回の差分が具体的に依存する不変条件と、保証されない場合の実質的な影響を説明できるものだけにする。外部システムの任意の障害や契約違反を仮定した一般的な防御論は含めない。
- リポジトリ内に外部契約の根拠がある場合は専用セクションへ残さず、その根拠に従って通常の指摘へ昇格するか除外する。
- 外部契約が未確認の候補について、未知の挙動を再現するテストがないことをテスト不足として重複報告しない。
- 指摘とテスト不足はそれぞれ重要度順、パフォーマンス計測候補は想定される影響が大きい順に並べる。
- 同じ原因から生じる指摘は統合し、1項目1論点とする。
- 一つの原因に由来するレイヤ責務と単一責任の問題は、必要に応じて統合する。
- コード欠陥とテスト不足を重複して報告してよいが、それぞれの目的を分けて記述する。
- 該当項目がないセクションには`該当なし`と記載する。
- 不確実性は、外部システム契約以外で結論を左右するものだけを一行で記載する。
- 変更概要、肯定的な所感、一般論、網羅的なチェックリストは追加しない。
