# Review contract

この文書は、指摘を出すための証拠水準と、必須観点の判定基準を定める。

## 証拠の扱い

観察したコードと実行結果を事実として扱い、そこから導いた失敗シナリオは推論として区別する。関連仕様、利用経路、既存テストを確認できない場合は、都合のよい挙動を推測しない。

指摘には、次のすべてが必要である。

- 今回の差分と結び付く`path:line`の根拠
- 問題が顕在化する条件または将来の誤変更経路
- 事業、ユーザー、セキュリティ、保守に対する実質的な影響
- 実行可能な対応案または確認方法
- `高`または`中`の確信度

確信度が低い候補は指摘にしない。外部契約次第で正否が変わる候補は専用セクションへ、それ以外は不確実性として報告する。今回の差分で悪化していない既存問題、一般的なベストプラクティス、命名や整形の好みは報告しない。ただし、既存コードが変更後の仕様を成立させない場合、または今回の差分によって新たに到達可能になる場合は、今回の変更に対する指摘として扱う。

## レビュー対象と外部システムの責務境界

レビュー指摘は、レビュー対象リポジトリが所有する実装、明文化された契約、既存挙動から問題を成立させられるものに限る。外部システムが仕様どおり動作しても発生する問題、またはリポジトリ内で確認できる外部契約に反する実装は、通常の指摘として扱う。

外部システムの契約が確認できず、その契約次第で正否が変わる候補は、`Must`/`Should`にせず「外部システム契約に依存する確認事項」へ分離する。次のすべてを満たす場合だけ報告する。

- 今回の差分が、特定の外部不変条件へ新たに依存する、または従来持っていた耐性を弱める。
- リポジトリ内の仕様、client、テスト、関連資料から、その不変条件を確認できない。
- 不変条件が満たされない場合の入力または応答と、事業、ユーザー、セキュリティ、保守への実質的な影響を説明できる。
- 確認すべき仕様、資料、担当システムなど、候補を解決する確認先を示せる。

外部障害、契約違反、不正形式を無制限に仮定した一般的な防御論は報告しない。リポジトリがその障害を処理すると明示している場合、既存実装が同じ障害へ具体的な耐性を持っていた場合、またはセキュリティ境界として検証が必要な場合に限って扱う。

外部契約を確認できた後は、次のように再分類する。

- 契約がリポジトリ側の前提を保証する場合: 候補を除外する。
- 契約が前提を保証せず、今回の差分で具体的な問題が成立する場合: 通常のレビュー指摘へ昇格する。
- 契約外の異常時だけに生じる場合: リポジトリがその異常への耐性を所有すると明示していなければ除外する。

## 1. 既存挙動、事業、ユーザーへの不利益

変更された仕様、不変条件、公開契約を特定し、実装箇所から利用経路まで追跡する。共有処理は、1つの呼び出し元だけで代表させず、意味の異なる利用経路を個別に確認する。

特に次を確認する。

- 正常系、境界値、不正・空・重複・古い入力
- API、イベント、永続データ、設定、既存クライアントとの互換性
- 途中失敗、部分成功、再試行、二重実行、並行実行
- トランザクション、後片付け、ロールバック、エラー伝播
- 課金、権限、重要データ、削除・上書き、広範囲な一括処理

失敗の可能性だけでなく、誰にどのような不利益が生じるかまで説明できる場合に指摘する。

## 2. セキュリティ

すべての差分でセキュリティ境界への影響を確認する。関連する変更がある場合は、入力元から保護対象と副作用までデータフローを追跡する。

確認対象には次を含む。

- 認証、認可、所有権、テナント境界
- 入力検証、パス・クエリ・コマンド生成、ファイル処理
- 個人情報、機密情報、トークン、Cookie、秘密情報、ログ
- 外部通信、リダイレクト、Webhook、依存関係、実行権限
- エラーや応答による情報漏えい、過剰な権限、既定値の変化

抽象的な脅威を列挙せず、攻撃または漏えいが成立する入力、権限、経路を説明する。成立条件を確認できない重要な懸念は、外部契約次第なら専用セクションへ、それ以外は不確実性へ移す。

## 3. 理解容易性と変更容易性

コード量の多さや短さ自体を評価しない。正しさや変更影響を判断するために、不必要に多くのファイル、抽象、暗黙知を読み込ませる構造を対象とする。

次のような構造が、具体的な誤変更またはレビュー負荷につながる場合だけ`Should`として報告する。

- 同じ業務ルールや権限条件が複数箇所に分散・重複している。
- 過剰な間接化により、入力から副作用までのデータフローを局所的に追えない。
- 重要な不変条件が命名、型、境界ではなく、呼び出し順や暗黙の前提に依存している。
- 条件の組み合わせや状態遷移が、既存テストでも意図を説明できない。

「読みづらい」「複雑である」だけでは指摘しない。どの将来変更で何を見落としやすいかを説明する。

## 4. アーキテクチャ上の責務と単一責任

リポジトリで明文化された責務、依存方向、境界に対して、変更された処理の所有者と新しい依存を評価する。単一責任は処理の数や長さではなく、独立して発生し得る変更理由の結合として評価する。詳細な証拠の探索順、判定手順、差分分類は [architecture-responsibility.md](architecture-responsibility.md) に従う。

指摘には、適用される方針の根拠、コードの根拠、混在する独立した変更理由、具体的な誤変更経路、および差分との関係が必要である。最終報告へ残すのは、今回の差分で`introduced`または`worsened`と確認できる問題だけとする。比較元にも存在し今回悪化していない問題、一般原則だけに基づく断定、設計上の好みは報告しない。

レイヤ責務違反と単一責任違反は原則として`Should`とする。既存契約の破壊、認可漏れ、データ不整合などの具体的な現在障害が成立する場合だけ、既存の重要度基準に従って`Must`とする。「設計原則に違反している」という理由だけで`Must`にしない。

## 5. 仕様をアサートするテストの不足

変更された仕様または不変条件ごとに、実装箇所、意味の異なる利用経路、テスト、アサーションを対応付ける。ここでの「直接アサート」とは、単体テストに限らず、その仕様に固有の観測可能な結果を明示的に検証することを指す。

内部ではテスト証拠を次のように分類する。

- `explicit`: テスト名、入力、操作、アサーションが対象仕様を明示し、仕様を破れば失敗する。
- `indirect`: 対象経路は実行するが、広いスナップショットや別の結果しか確認していない。
- `absent`: 対応するテストまたはアサーションがない。
- `unclear`: テスト、仕様、実行経路の不足により判定できない。

次の手順で判定する。

1. 変更された仕様または不変条件を一文で表す。
2. 対応するテストの入力、操作、期待結果を特定する。
3. 変更前の実装または仕様を破る実装でも、そのテストが成功しないか反実仮想的に確認する。
4. `absent`、または対象仕様を証明できない`indirect`なら、最終報告の独立セクションへ含める。
5. `unclear`ならテスト不足と断定せず、不確実性へ含める。

テスト不足には、対象仕様、実装箇所、現在のテスト証拠、不足するアサーション、具体的な推奨テストを必ず記載する。優先度は、セキュリティ、重要な事業ルール、不可逆な副作用、広い利用経路を守るものを`高`、それ以外の変更仕様を`中`とする。`低`は使用しない。

外部契約が未確認の候補について、その未知の挙動を再現するテストがないことをテスト不足として重複報告しない。契約を確認し、リポジトリ側が保証すべき仕様だと確定してからテスト不足を判定する。

## 指摘の分類

### Must

今回の差分により、既存契約の破壊、誤った事業処理、ユーザー被害、セキュリティ侵害、データ不整合、復旧困難な障害が具体的に起こりうる問題。

### Should

現時点の欠陥を断定できなくても、今回導入された構造が将来の誤変更やレビュー負荷を実質的に増やし、差分の範囲で改善する価値がある問題。書き方の好みや「きれいにする」だけの提案には使用しない。

## 不確実性

外部システム契約以外で、結論を左右する不明点だけを報告する。各項目には、判断できないこと、重要な理由、確認に必要な情報を含める。単にCIや仕様書が提供されていないという理由だけでは報告しない。外部契約次第で正否が変わる候補は、上記の専用セクションへ分類する。
