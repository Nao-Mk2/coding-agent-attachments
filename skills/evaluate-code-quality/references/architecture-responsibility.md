# Architecture and responsibility review

この文書は、リポジトリで明文化されたアーキテクチャ上の責務、依存方向、境界、および単一責任を評価する手順を定める。特定のレイヤ名、ディレクトリ構成、業務用語、実装パターンを前提にしない。

## 比較対象を固定する

PRでは、調査前にbase SHAとhead SHAを確定し、主担当とsub-agentで共有する。次の形式を優先する。

```text
git diff <base_sha>...<head_sha>
git show <head_sha>:<path>
git show <base_sha>:<path>
```

作業中のHEAD、index、working treeをPRの証拠にしない。共有worktreeへ別の変更が入っても、固定した比較対象を変えない。stagedレビューではindex上の内容だけを対象とし、unstaged差分を混ぜない。

## 設計方針を発見する

リポジトリ固有の責務と依存方向は、次の情報源から対象範囲に適用される記述を探す。

- `AGENTS.md`
- `CONTRIBUTING.md`
- README
- `docs/`以下の設計資料とADR
- パッケージやモジュールの説明
- 依存方向を定める設定や静的検査
- 同じ責務を持つ既存の実装と利用経路

設計方針の証拠は、次の優先順で評価する。

1. 比較元に存在するプロジェクト指示と設計資料
2. 対象範囲に適用されるADRやモジュール規約
3. 同じ責務を持つ既存の利用経路
4. PRで追加または変更される設計資料
5. 一般的な設計原則

PRで追加または変更された資料は、確立済みの規則ではなく提案された変更として評価する。その資料だけを根拠に、同じPRの実装を自動的に正当化しない。既存資料と新しい資料が競合する場合は正しさを推測せず、不確実性として扱う。明示された例外、適用範囲、優先規則を確認し、一律に適用しない。

明文化された方針が見つからない場合は、一般原則をリポジトリ固有の規則として断定しない。一般原則だけでは具体的な誤変更経路に確信を持てない問題は、指摘ではなく不確実性として扱う。同じリポジトリの既存実装は方針や一貫性を理解する補助証拠にできるが、「既存コードも同じ構造だから正しい」とは判定しない。

## レイヤ責務と依存方向を判定する

最初に、変更された処理を設計資料上の所有者へ対応付ける。必要に応じて内部で次の表を作成する。

| 変更された処理 | 規定上の所有者 | 実装場所 | 方針の根拠 |
| --- | --- | --- | --- |

次を確認する。

- 新しい依存が、明文化された依存方向へ反していないか。
- 外部システム固有の型や制約が、規定された内部境界へ漏れていないか。
- 業務判断が、本来の所有者以外で再構築されていないか。
- 永続化、外部通信、認可、エラー変換などの責務が、方針に反して分散していないか。
- 境界型が、複数の層や利用者の都合を同時に背負っていないか。
- 利用側が、不要な操作まで含む広すぎるinterfaceへ依存していないか。

規定上の所有者と実装場所が異なるだけで指摘にしない。適用される方針の根拠、新設または悪化した依存・責務、そこから生じる具体的な失敗または誤変更経路を結び付ける。

## 単一責任を変更理由として判定する

責任は、処理数、関数の長さ、メソッド数、抽象の少なさではなく、独立して発生し得る変更理由として評価する。対象となる型、関数、interface、モジュールについて、変更契機を特定する。

変更契機の例には、次がある。

- 外部プロトコルやスキーマの変更
- 業務ルールの変更
- ユースケースの実行順変更
- ページングや公開契約の変更
- 永続化方式やトランザクション境界の変更
- 表示形式やシリアライズ形式の変更
- 認証や認可方式の変更

複数の独立した変更契機が同じ単位へ結合し、片方の変更時にもう片方を誤って変更する経路、または確認範囲が増える保守コストを具体的に説明できる場合だけ指摘候補にする。複数の処理を順番に実行するオーケストレーションは、それだけでは単一責任違反にしない。

候補には、混在する変更理由と、片方を変更したときに誤りやすい対象を含める。

## 差分との関係を分類する

すべての候補を次のいずれかへ分類する。

- `introduced`: 今回の差分で新しく導入された。
- `worsened`: 比較元にある問題の影響範囲、依存、責務の混在が今回の差分で拡大した。
- `pre-existing`: 比較元にも同じ問題があり、今回の差分で悪化していない。
- `unclear`: 固定した比較対象から差分との関係を確認できない。

最終的なレビュー指摘へ残せるのは`introduced`または`worsened`だけである。変更行が既存問題をそのまま利用しているだけでは`worsened`にしない。影響範囲、依存、責務の混在が実際に増えた証拠を必要とする。`pre-existing`は今回のPRに対する指摘として報告せず、`unclear`は結論を左右する場合だけ不確実性として扱う。

## 指摘候補の返却

専用sub-agentは変更概要やdiffを再掲せず、次の候補だけを返す。

- 分類: `Must` / `Should`
- 観点: `レイヤ責務` / `単一責任`
- タイトル
- 方針の根拠: `path:line`
- コードの根拠: `path:line`
- 差分との関係: `introduced` / `worsened` / `pre-existing` / `unclear`
- 独立した変更理由
- 発生条件または将来の誤変更経路
- 影響
- 対応案
- 確信度: `高` / `中`

候補がない場合は、`該当なし`とだけ返す。

レイヤ責務違反と単一責任違反は原則として`Should`とする。既存契約の破壊、認可漏れ、データ不整合など、現在の具体的な障害が成立する場合だけ、`review-contract.md`の既存基準に従って`Must`にする。設計原則への違反だけを理由に`Must`にしない。
