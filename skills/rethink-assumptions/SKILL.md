# Rethink assumptions

ユーザーや関係者が選び直せることを、動かせない条件として扱っていないか確かめる。ユーザーが達成したいことを基準に、ひとまず固定していた前提を見直す価値を判断する。疑うこと自体を目的にせず、現在案を続けるか、変更するかを決められる材料を整える。

## 1. 前提を洗い出す

目的と成功条件を短く確認し、達成したいことと、そのために指定・想定された手段を分ける。依頼、既存の計画、仕様、コード、運用の事情から、案を縛っている前提を拾う。期限、費用、対象範囲、採用技術、既存構成、更新頻度、担当者の役割など、判断への影響が大きいものを優先する。

目的や成功条件も、ユーザーの選択による部分は定数とみなさない。ただし現在の目的を比較の基準とし、その変更を伴う案では何が変わるかを明示する。

最初は重要な3〜5件を目安に絞る。各前提について、出所、固定している理由、根拠の確かさ、変更を判断できる人を確認する。ユーザーの指定、確認済みの事実、慣例、AIの推測を混同しない。

## 2. 定数と変数に分ける

- **定数**: ユーザーの意思によらず、この課題で必ず守る必要がある制約。実際に適用される法律、倫理上の義務、避けられない物理的・技術的な限界などが該当する。
- **変数**: それ以外の、意思決定によって選び直せる前提。ユーザーの指定、過去の合意、既存方針、採用技術、自ら設定した予算や期限なども含める。現在は維持しているものは、**ひとまず固定している変数**として扱う。

「変更には合意が要る」「変更の負担が大きい」「すでに決まっている」は、定数とする理由にならない。**変数であることと、AIが変更してよいことを分ける。** 必要な合意を得るまでは現在の指定を守る。

法律・倫理・技術に関係するというだけで定数と断定せず、何が、どの条件のもとで必須なのかを確認する。根拠や区分がわからない場合は「要確認」と注記し、動かせないとも自由に変更できるとも決めつけない。

必要に応じて次の表で整理する。表を毎回ユーザーに見せる必要はない。

| 前提 | 定数／変数・現在の扱い | 根拠・確かさ・適用条件 | 変更に必要な条件・判断者 |
| ---- | ---------------------- | ---------------------- | ------------------------ |

## 3. 定数の根拠と、固定している変数を見直す

動かせないと思っていた前提を中心に、影響の大きいものから次を確かめる。

- 定数と判断した根拠は確かか。実際には、ユーザーの指定、以前の都合、慣例、推測で固定した変数ではないか。
- 特定の環境や方法を選んだ場合だけ必要な条件ではないか。その環境や方法の選択自体を変えれば、制約の適用を避けて目的を満たせないか。
- ひとまず固定している変数を選び直すと、何が簡単になり、どの成果が改善するか。実際に変えるには何を確認し、誰と合意する必要があるか。

たとえば、採用中の基盤に処理時間の上限がある場合、その基盤では上限を守る必要がある。一方、「その基盤を使い続ける」は変数なので、処理の分割や基盤の変更も比較する。制約そのものと、その制約が適用される選択を分ける。

手元の資料、コード、必要に応じて公式情報を確認し、確認できないことは不明と記す。本当に必須の制約は守る。その制約を仮に消しただけの案は実行案とせず、実行可能な選択肢と成立条件を示す。

## 4. 現在案と代替案を比べる

現在の前提を維持する案を基準に、有望な代替案を1〜2案に絞る。目的の達成度、作業量と費用、変更・移行の手間、運用負担、主な不利益、元に戻せるかを、判断に関係する範囲で比べる。既に費やした労力と、これから切り替えるために必要な労力を分ける。

改善が見直しや切り替えの負担に見合うかを判断する。成果や品質を減らす案は、その差を明示し、同じ成果を安く達成する案と混同しない。推測の数値や未確認の期待だけで優位と決めない。

比較に必要な調査や小さく元に戻せる検証は、既に許された範囲で先に行い、相談できる具体案まで整える。調査は判断を変えうる不明点に絞る。不確実さが残る場合は、条件付きの改善案または検証案として示す。

## 5. 改善案を報告し、最終対応を決める

より良い案が見つかったら、次の内容を短くまとめてユーザーに報告・相談する。

- **見直した前提**: 何を動かせないと思っていたか。何が本当の定数で、何がひとまず固定していた変数か。
- **具体案と比較**: 現在案から何を変え、何が良くなり、どんな不利益や変更負担があるか。
- **根拠と未確認点**: 確認できたこと、まだわからないこと、成立に必要な条件。
- **推奨と相談事項**: 推す案とその理由、ユーザーに決めてほしい点。

変更した前提に依存する本実装や外部への反映は、ユーザーと最終対応を決めてから進める。調査や比較を始めるだけの確認は求めない。すでに同じ変更について合意がある場合は、再度の承認を求めず、その合意と判断結果を報告する。相談待ちでも、判断に影響されない、既に許された作業は進めてよい。

より良い案が見つからない場合は、現在案を続ける。報告が有益なら、維持する理由だけ簡潔に添え、確認のためだけの質問を増やさない。

## 見直しを終える

決まった対応、採用・不採用の理由、変更した前提と未確認点を、既存の計画や作業記録に必要な範囲で反映する。このスキルのためだけに新しい管理場所を増やさない。追加の検討で判断が変わりそうにない時点で終え、同じ根拠のまま決定を蒸し返さない。新しい事実や制約が出たときだけ再検討する。
